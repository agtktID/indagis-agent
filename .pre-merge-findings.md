## Ticket A : `tests/agent/test_anthropic_output_field_leak.py` pollue sys.path avec le chemin upstream

**Fichier**: `tests/agent/test_anthropic_output_field_leak.py:13-14`

```python
import sys, os
sys.path.insert(0, os.path.expanduser("~/.hermes/hermes-agent"))
```

**Symptôme**: à la collection pytest, le module importe `hermes_cli.config` (transitivement) qui fait `from hermes_constants import get_indagis_home`. Comme `~/.hermes/hermes-agent/hermes_constants.py` est préfixé sur `sys.path`, Python charge la version upstream (qui n'a pas `get_indagis_home` — elle s'appelle encore `get_hermes_home` là-bas). ImportError → les 4 tests du fichier sont marqués ERROR en collection.

**Reproduction** (sortie littérale):
```
ImportError: cannot import name 'get_indagis_home' from 'hermes_constants' (/home/user/.hermes/hermes-agent/hermes_constants.py)
/home/user/Documents/indagis-agent-work/hermes_cli/config.py:691: ImportError
```

**Cause racine**: résidu du rebrandage `hermes_agent` → `indagis_agent`. Le test force-load explicitement le chemin upstream `~/.hermes/hermes-agent/`, ce qui shadow l'import local. Les autres tests agents n'ont pas ce hack et fonctionnent. Le fichier semble avoir été adapté pour l'API upstream avant que le fork ne rename, et le hack `sys.path` n'a jamais été retiré.

**Indice de nettoyage incomplet**: cohérent avec l'enquête des 7549 occurrences de chaînes `hermes_agent`/`hermes-agent` non encore tranchées.

**Statut**: bug préexistant, indépendant de PR #10 (vérifié identique sur commit parent `a9d15569a` via worktree).

**Fix proposé** (à discuter):
1. Supprimer les lignes 13-14 (le test n'a pas besoin du chemin upstream pour fonctionner)
2. OU: si le test dépend vraiment d'un mock situé dans `~/.hermes/hermes-agent/`, mocker via `monkeypatch`/fixture pytest plutôt qu'un `sys.path.insert`

## Ticket B : `tests/test_hermes_state.py` dépasse le timeout fichier de 600s

**Fichier**: `tests/test_hermes_state.py`

**Symptôme**: 165 tests collectés, le runner parallèle les tue à 600.1s (24% / 40 tests exécutés). Marqué "no tests ran" dans le rapport final — aucun des 165 tests ne compte dans la métrique pass/fail.

**Cause racine**: la batterie SQLite/JOURNAL_MODE/FTS5/PRAGMA est intrinsèquement lente sur ce hardware (chaque test ouvre une DB, applique des pragmas, exerce le WAL). Fichier identique entre `a9d15569a` et `baff6db77` (vérifié `diff -q` byte à byte).

**Statut**: bug préexistant, indépendant de PR #10. Slowness, pas une régression.

**Variance d'un run à l'autre**: ce fichier est un contributeur probable à l'écart "95 vs 91" observé entre deux snapshots — il frôle la frontière du timeout et la fluctuation de charge CPU fait varier le nombre de tests qui finissent dans la fenêtre.

**Fix proposé** (à discuter):
1. Augmenter `HERMES_TEST_FILE_TIMEOUT` localement pour ce fichier (mais le runner parallèle ne supporte pas les overrides per-file — ce serait un changement de design)
2. Découper le fichier en plusieurs morceaux plus rapides (e.g. un fichier par classe de tests: SQLite CRUD / FTS5 / Journal Mode / Pragma Performance)
3. Optimiser les tests lents (utiliser `:memory:` SQLite partout au lieu de fichiers temporaires quand c'est possible)
4. Marquer les tests les plus lents avec un marker custom pour les sortir du CI rapide

## Observation C — `~/.hermes` est le profil de travail réel, `~/.indagis` est secondaire (2026-08-10)

**Contexte** : pendant la discussion sur le trust model P2 (cf.
`reports/plan-get-indagis-home-resolution.md` section "Décision actée — Tranche
1 P2 trust model (2026-08-10)" et `apps/desktop/README.md` section "Priority 2
trust model"), j'avais initialement inféré que `~/.indagis` était le profil de
travail et `~/.hermes` l'ancien profil abandonné. **Cette inversion était
fausse** — corrigée après vérification factuelle par l'opérateur 2026-08-10.

**Faits observés** (sortie littérale `du` / `which` / `cat config.yaml`) :

| Répertoire | Taille | Profil / config | Verdict |
|---|---|---|---|
| `~/.hermes` | **9,8–10 GB** | Contient `profiles/pentest/sandboxes/docker/default/home/` avec de vrais outils de sécurité configurés (`nuclei-templates`, `naabu`, `ffuf`, `katana`, `dnsx`, `subfinder`, `httpx`, `john`, `bb-workdir`, `go/`, `bin/`, `install_pentest_sandbox.sh`). `config.yaml` (mtime 2026-08-06) déclare `model: MiniMax-M3, provider: minimax-oauth` actif. `which hermes` → `/home/user/.local/bin/hermes`. L'opérateur utilise `hermes` au quotidien (historique shell : dizaines d'usages récents dont aujourd'hui). | **Profil de travail réel et actif.** |
| `~/.indagis` | **2,7–2,9 GB** | Créé le 1er juillet 2026 par une install initiale du fork (`hermes-agent/venv/bin/python`). Premier fichier applicatif (`projects.db`) le 6 août. `auth.json`, `state.db` à partir du 8 août. Modifications les plus récentes (2026-08-10 06:24) = nos propres tests de cette session (pass `scripts/run_tests.sh` qui ont muté `INDAGIS_HOME` via la garde hermétique). | **Profil secondaire**, créé tôt mais peu utilisé au quotidien. |

**Conclusion corrigée** : **`~/.hermes` est le profil de travail réel et actif**
de l'opérateur ; `~/.indagis` est un profil secondaire (créé tôt par l'install
initiale du fork, peu utilisé depuis — l'essentiel de son contenu récent date
des tests de cette session). Les deux profils coexistent légitimement, et
cette coexistence est le cas d'usage prévu par P2 + P4 du ladder (un
utilisateur peut avoir un profil Indagis secondaire sans avoir migré son
profil principal Hermes).

**Implications sur le trust model** : la décision **Option B** (résolveur
silencieux, garde anti-pollution dans le tooling) reste valide, mais la
justification factuelle est corrigée. La formulation canonique ("P2 suppose
un `~/.indagis` créé par un install de confiance") décrit toujours bien le
contrat — `~/.indagis` peut légitimement coexister avec `~/.hermes` quand
l'opérateur n'a pas migré, et le résolveur a raison de le retourner en
silence (P2 gagne, P4 warning est légitime mais n'est pas consulté parce
que le helper pur est appelé).

**Garde anti-pollution** : voir la décision actée, action annexe. Le test
qui vit dans `tests/conftest.py` après le fix est conçu pour détecter
**uniquement les vraies pollutions** (test qui crée `~/.indagis` ou
`~/.hermes` durant une session pytest) — pas les coexistences légitimes
comme celle-ci.

**Méthodologie — leçon apprise** : la première itération de cette
observation avait extrapolé depuis les mtimes de fichiers sans vérifier le
contenu fonctionnel des deux profils. Une session de travail n'est pas
déterminée par les dates de fichiers mais par l'usage réel (historique
shell, binaire dans le PATH, config active). Une investigation qui ne
vérifie pas l'usage actif risque d'inverser la cause et la conséquence.

**Statut** : observation corrigée, intégrée à la doc. Pas de ticket ouvert.
